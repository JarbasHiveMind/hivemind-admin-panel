# AGENTS.md — `hivemind-admin-panel`

Guidance for AI coding agents (and humans) working in this repository. Read it
fully before making changes. It encodes conventions that are not obvious from the
code and that, if ignored, produce work that will be rejected.

## Repo

A web-based administration panel for [HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core).
It is the single launcher for a HiveMind hub: it starts `hivemind-core` in-process
(native mode, no separate hub process) and serves the admin UI over FastAPI, so
one command gets both a hub and a place to administer it — clients, ACLs, plugins,
databases, personas, chat bridges, and OVOS-server registration. Part of the
[HiveMind](https://github.com/JarbasHiveMind) ecosystem — a protocol for
connecting satellite devices to a hub running
[OpenVoiceOS](https://github.com/OpenVoiceOS). Related repos:
[HiveMind-core](https://github.com/JarbasHiveMind/HiveMind-core) (the hub this
panel owns), [hivemind-bus-client](https://github.com/JarbasHiveMind/hivemind-bus-client)
(used directly for the client-impersonation Test Chat), and
[hivemind-plugin-manager](https://github.com/JarbasHiveMind/hivemind-plugin-manager).

## Layout / build / test

- Package module: `hivemind_admin_panel/`. Tests live in `tests/` (check before
  adding — do not create a second test directory). `integration/` holds separate
  end-to-end scripts, not part of the pytest suite.
- Set up a throwaway environment inside your clone; never touch a shared venv:
  `python3 -m venv .venv && VIRTUAL_ENV=$PWD/.venv uv pip install -e ".[dev]" --prerelease=allow`
- Run the suite in the foreground: `python3 -m pytest tests -q`.
  The `test` and `dev` extras pin `httpx<1.0`: starlette's `TestClient` needs
  `httpx.BaseTransport`, which httpx 1.0 removes, and this repo otherwise resolves
  with prerelease floors that pick up httpx 1.0 dev builds.
- `uv`, never `pip`. If latest prereleases fail to install or resolve, that is a
  bug to FIX at the source, not to work around with a pin downgrade.

## Working agreement (org-wide law)

- **Git identity is always** `JarbasAi <jarbasai@mailfence.com>`. Never set a
  per-repo override.
- **Never push `dev` or `master`.** Work on a feature branch and open a
  **draft** PR into `dev`. A human merges. You do not merge your own PRs.
- **Never merge or modify `Release X → master` PRs.** They are the maintainer's
  stable-release mechanism, generated by automation.
- **One commit per PR** (squash before pushing). Conventional commits; `feat:`
  only for a user-visible new capability. `fix:`, `docs:`, `chore:`, `ci:`
  otherwise.
- **Disclose AI authorship.** Every PR/issue/comment an agent writes carries, at
  the top: `> 🤖 Auto-generated by <model> via Claude Code — NOT human-reviewed.
  Verify before acting.` PR bodies are plain human prose (3–6 short paragraphs),
  no tables or section-symbol spray.
- **Never edit someone else's** issue, PR description, or comment. Add a comment
  instead; on your own PRs, edit the body rather than piling on comments.
- Keep durable text (README, docs, PR bodies, comments) timeless and standalone:
  no dates, no "currently/now/new", no meta-commentary about the edit itself.
- No scratch files, committed virtualenvs, `__pycache__`, `.pyc`, `.egg-info`,
  or build artifacts in a PR. `git show --stat` shows only intended files.
- **Keeping this AGENTS.md current is a quality gate.** Any PR that changes this
  repo's conventions, build/test commands, dependencies, entry points, or
  observable behavior updates AGENTS.md in the same PR. A stale AGENTS.md is a
  review-blocking defect, the same tier as a failing test.

## Dependencies

- **Floor pins only** (`>=X.Y.Za1`), bumped when a feature or fix is actually
  needed — with a one-line comment saying why. No upper caps unless a specific
  released version is genuinely broken (say which and why; see the `httpx<1.0`
  and `hivemind-bus-client<2.0.0` comments in `requirements.txt` for the pattern).
- **No lockfiles, ever.** Target the latest alphas (`--prerelease=allow`).
- Dependencies live in `requirements.txt` (pulled dynamically into
  `pyproject.toml`); test-only deps live in `pyproject.toml`'s `test`/`dev`
  extras. Version comes from `hivemind_admin_panel/version.py`. Never install
  from git — depend on a published PyPI alpha.
- Apache-2.0. Do not add GPL/AGPL dependencies. The panel deliberately targets
  the Apache-licensed `hivemind-core>=4.6.1a1` floor over the AGPL-3.0 stable
  4.0.0 release — keep new dependencies on the same Apache-licensed alpha track.

## Tests

- Adversarial by default. A regression test must **fail before the fix and pass
  after** — prove it by reverting only the source (`git apply -R`, never
  `git stash` across worktrees) and watching the test flip.
- Tests must be mutation-proof: gutting the feature must fail the test. A test
  that only asserts a mock was called, without asserting the real behaviour, is
  weak — note it.
- Never skip a test because an optional dependency is missing.
- CI green is permission to review, not to merge. A non-trivial change gets an
  adversarial review before it lands.

## Repo-specific rules

- This is the admin plane over the hub bus: it starts `hivemind-core` in-process
  and holds a live reference to it, so `hivemind-core` itself carries no
  admin-specific code. Installs are bus-only — do not add code paths that reach
  into the hub's internals other than through its documented bus/client API.
- The `--host` default is `127.0.0.1` (loopback-only) for a reason: the panel can
  install packages and migrate databases, so it must never default to a public
  bind. Where a deployment needs to reach the panel from other nodes on a Tailnet
  or LAN, that is an explicit `--host <tailnet-ip>` (or `0.0.0.0` behind a
  trusted reverse proxy) at launch time, never a change to the default, and
  `docs/security.md` / `docs/troubleshooting.md` should stay the source of truth
  for that guidance rather than duplicating it here.
- Newly created client credentials (`api_key`, `password`, `crypto_key`) are
  generated server-side and returned once in the creation response — see
  `api.py`'s `ClientCreate`/`ClientResponse` models and the `access_key =
  data.api_key or os.urandom(16).hex()` flow. They must never be logged, and any
  UI or endpoint that re-displays them after creation must re-authenticate the
  request rather than caching or persisting the plaintext for later retrieval.
- `admin_pass` and the token-signing secret live in `server.json`
  (`~/.config/hivemind-core/server.json` by default); `_auth.py` hashes
  passwords with PBKDF2 and rotates the signing secret on password change to
  invalidate outstanding bearer tokens. Preserve that fail-fast invalidation
  when touching auth — a stale token surviving a password change is a security
  regression, not a convenience bug.
- Config-mutating operations (server.json edits, plugin install/uninstall,
  database migration) snapshot the prior state first so `docs/operations.md`'s
  diff/revert flow keeps working; don't add a mutation path that skips the
  snapshot.
